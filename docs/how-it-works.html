01 The one decision

Everything in the system exists to answer a single question, over and over.

When an AI agent proposes to change something on real infrastructure, Assent decides one thing:

The question

Is this action safe enough to run by itself — and if not, who specifically has to say yes?

There are exactly three answers, and every path through the system lands on one of them:

OutcomeMeaningWho acts
auto The measured risk of taking this action is low enough that it runs immediately Nobody — logged and reversible
route to owner Needs a human, and we know with confidence who owns the affected system That owner
escalate Needs a human, and either no confident owner exists or a safety rule tripped Broadened — a wider group

The critical framing: Assent scores risk-to-act, not threat severity. A reversible, narrow, non-production change stays low-risk even during a critical incident — and a tiny change to a payment system stays high-risk on a quiet Tuesday.

02 The invariant

One rule decides which parts of the system are allowed to be AI at all.

The invariant

An AI model may produce any input that makes the gate more conservative. Anything that could relax the gate is measured by code.

This is the load-bearing idea, and it sorts every variable in the system onto one side of a line. Things that can open the gate — how reversible an action is, how many systems it touches, whether it's production, who owns it — are measured from infrastructure, catalogs and code. Things the model produces — its confidence, its written reasoning — can only ever push toward a human.

This is the deliberate break from how the rest of the market gates AI actions. The current bar is "if the model is >99% confident, act." Model confidence is poorly calibrated, and an attacker who can influence the inputs can manufacture it. So in Assent, confidence never authorizes anything — it only ever withholds.

03 The pipeline

What actually happens between a detection arriving and something changing.

Note what the model is not trusted to do: it never measures its own blast radius, never decides reversibility, never picks the owner, and never executes. It picks an action from a fixed catalog and states how sure it is. That's the whole surface.

04 The risk envelope

Four axes, each with a specific source. Three of them are facts; one is an opinion.

risk_envelope = blast_radius × reversibility × environment × confidence
AxisWhat it measuresWhere it comes fromCan open the gate?
blast_radiusHow many systems/users the action touches Inventory: 1 + dependentsmeasured
reversibilityWhether it can be cleanly undone Action catalog, per action typemeasured
environmentdev / staging / prod Inventory metadata for the targetmeasured
confidenceHow sure the agent is about the diagnosis The modeltightens only
hits_tier0Whether the target is a crown-jewel system Inventory flagmeasured

Reversibility is a property of the action, not the situation

It's classified once, in code, per action type — so it can't be argued down in the moment. The catalog is the safety boundary: an action that isn't in it cannot be proposed at all.

ClassMeaningActions in the current catalog
reversibleClean, automated undo block_domain, quarantine_host, disable_user_session
recoverableUndo possible, but with cost or latency rotate_credential, revoke_iam_role
irreversibleNo undo — never auto-executes delete_volume, terminate_instance

Where the catalog and the proposed envelope disagree, the more conservative classification wins. An agent claiming a volume deletion is reversible doesn't get to make it so.

05 Scoring the gate

Auto-execution is a checklist, not a score to beat. Every item must pass.

There is no weighted total here, deliberately — a single high number can't buy its way past a hard limit. These are the shipped defaults, and each is a per-customer dial that can only be made stricter than the measured facts allow:

SettingDefaultEffect
Environments eligible for autodev, stagingProduction writes never auto-execute
Max blast radius for auto5Anything wider goes to a human
Tier-0 systems may autofalseCrown jewels always gated
Reversibility required for autoreversibleRecoverable and irreversible always gated
Rollback plan requiredyesNo undo plan ⇒ no autonomy, ever
Confidence floor for auto0.85Below this, a human decides — it never authorizes
Owner confidence to route0.75Below this, escalate rather than guess an approver
Max acting-vs-audit divergence0.25Wider disagreement escalates on its own

Order of evaluation

The sequence matters, because the early exits are the safety story:

1. action not in catalog → escalate 2. action is a read → auto (reads are always autonomous) 3. audit dissents or diverges → escalate 4. any AUTO checklist item fails→ gate (route if owner confident, else escalate) 5. effective confidence < 0.85 → gate · min(acting, audit) 6. doc-grounded caution flag → gate 7. otherwise → auto

Steps 3, 5 and 6 are the model-influenced ones — and note they appear only as ways out of auto-execution. There is no step where a model input moves a decision toward autonomy.

Reads are free. The real trust boundary is read vs. write, not environment. Querying posture, listing alerts, and investigating are fully autonomous — the gate only engages when something would actually change.

06 Scoring ownership

Who owns this system, how sure are we, and is that belief still fresh?

Approvals are worthless if they go to the wrong person, so ownership carries its own confidence score. Rather than demanding a company fill in a giant asset database, Assent derives ownership from systems that already encode it, and scores each claim by source and age.

TierSourceExamplesBaseHalf-life
1codeCODEOWNERS, git blame, Terraform, K8s labels0.90365d
2opsPagerDuty, Opsgenie, service catalogs0.8045d
3cloudResource tags, CMDB, EDR inventory0.6590d
4identityIAM policies, group membership0.60120d
5docsRunbooks, wikis, postmortems0.4030d
6humanA person confirmed it by approving0.98180d

Documents score lowest for a reason: the moment an attacker can write to a wiki, that wiki is untrusted input. A poisoned runbook can raise caution but can never grant permission.

Staleness decays a claim

confidence = base × 0.5 ^ (age_days / half_life_days)

A CODEOWNERS entry ages slowly; a PagerDuty rotation goes stale fast. Concrete decay of a code claim (base 0.90):

At 365 days that claim has fallen to 0.450 — below the 0.75 routing floor, so it can no longer silently route an approval. A stale belief stops being trusted without anyone having to notice.

Agreement across sources compounds

A cloud tag alone isn't enough to route a production change to someone — which is exactly what happens to chg-0004 in §09. Two independent sources agreeing is.

The flywheel

Every human approval writes a human-tier claim back into the graph. The system learns who owns what as a side effect of normal use — and it gets most accurate exactly where it's most active.

07 Scoring the second opinion

A separate reviewer that never sees the first one's answer.

A second agent independently scores how safe the action looks. The critical design choice: it never reads the acting agent's confidence. If it did, it would echo rather than check. It starts at 1.0 and multiplies down for each risk factor it measures itself:

FactorMultiplier
Target is production× 0.55
Target is staging× 0.97
Target is tier-0× 0.50
Action is recoverable (not cleanly reversible)× 0.80
Action is irreversible× 0.30
Blast radius× 1 / (1 + radius/20)
No rollback plan× 0.30
Doc-grounded caution raised× 0.70

Two ways the second opinion forces a human

Dissent — the auditor's score collapses below 0.20, or the action is one it can't classify at all. Divergence — the two agents disagree by more than 0.25. The disagreement itself is the signal; nobody needs to adjudicate who was right.

Worked example — chg-0002: rotate a leaked credential on payments-api
StepMultiplierRunning score
Start—1.0000
Production target× 0.550.5500
Tier-0 system× 0.500.2750
Recoverable, not reversible× 0.800.2200
Blast radius 5× 0.800.1760

The acting agent was 91% sure. The auditor landed at 17.6% and dissented. Assent escalated — and it would have escalated on the divergence alone (0.91 − 0.176 = 0.73, far past 0.25) even if the dissent floor hadn't caught it. Two independent reasons to stop.

08 When data is missing

The behavior that matters most is what happens when the system doesn't know something.

Incomplete data degrades to "ask a human," never to "guess and act." Gaps cost latency, not safety — which is what makes it viable to deploy before every integration is wired up.

What's missingWhat the system assumesResult
System not in the inventoryprod + tier-0 + radius 100cannot auto-execute
No owner on fileconfidence 0.0escalate, never guess an approver
Owner known but below 0.75belief too weak to act onescalate
No playbook for the signalno action is proposed at allhuman triage
Action not in the catalogrisk is unclassifiableescalate
No rollback planthe change is not undoablerefused at engine and executor

Note the last row: the rule is enforced twice, in two independent places. Even a caller that bypassed the policy engine entirely still can't strand an un-undoable change.

10 The audit ledger

Answering "who allowed this, and on what basis" — provably.

Every consequential moment is appended to a hash-chained log: the proposal, the decision and its reasons, the audit opinion, the execution, the human approval or denial, the rollback. Each entry commits to the hash of the one before it:

entry_hash = sha256( seq, timestamp, event, change_id, actor, detail, prev_hash )

Change any historical entry — a timestamp, an actor, a reason — and every subsequent hash stops reconciling. verify() walks the chain and names the first entry that breaks. The log isn't merely a record of what happened; it's evidence that the record hasn't been edited since.

This matters because "lack of accountability" is one of the named reasons security teams refuse to give agents write access. A log an operator can quietly amend doesn't answer that objection. A chain that detects amendment does.

11 Real vs. stand-in

What's built, and what's deliberately still a placeholder.

ComponentStatus
Policy engine — the gateReal, deterministic, 75 tests
Risk envelope + action catalogReal
Ownership graph — decay, corroboration, flywheelReal
Independent audit agentReal (rule-based reviewer)
Hash-chained ledgerReal
Approval queue + web appReal, runnable
Diagnosis — deciding which action responds to a threatStand-in: an explicit playbook, not an LLM
Execution against real infrastructureStand-in: simulated adapter

The ordering is intentional. The safety rails were built first, so that when a model is dropped into the diagnosis slot it can only ever propose within them — it inherits every constraint described above rather than needing to be trusted. The same is true of execution: the seam is designed to hand approved actions to enforcement infrastructure that already exists, rather than rebuilding it.

The bet

Everything here is engineering. The open question is commercial: under what exact conditions would a security team let an agent change production at all? That's answered by customers, not code — but it's a far easier conversation to have with a working system than a slide.
